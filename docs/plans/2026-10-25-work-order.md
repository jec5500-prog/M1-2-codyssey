## 1. 목표와 방향

사용자가 저장한 시계열 데이터의 기간·통계·추세를 이해하고 답하는 웹 AI 비서를 완성한다. 데이터 CRUD, 대화 수동/자동 저장 및 불러오기, Render/Vercel 배포, 재현 가능한 README와 제출 증빙을 모두 갖춘다. 보너스는 기존 도구 호출·시각화·CSV·다크 모드를 검증하고, 별도 MCP 클라이언트 연동까지 완성한다.

추천은 **기존 코드 보완**이다. FastAPI·Firestore·GPT API·바닐라 HTML/CSS/JS·Render·Vercel은 과제의 고정 조건이다. 기존 기능이 많아 재사용 가치가 높고, 마감까지 전면 재작성의 실익이 작다. 다른 프레임워크로 전환하지 않는다.

| 검토한 방향 | 장단점 | 제안 |
|---|---|---|
| 기존 코드 보완 + MCP stdio 어댑터 | 기존 UI/API 재사용, 별도 MCP 호스팅 불필요. 로컬 클라이언트 실행법 필요 | 사용자 승인 후 구현·실서비스 검증 완료 |
| 기존 코드 보완 + GPT Actions | 기존 HTTPS API 재사용. 외부 UI 계정·권한·스키마 등록에 일정 변수 | 예비안. MCP 연동이 불가능한 경우에만 검토 |
| 전면 재작성 | 테스트 기반 새 설계 가능하지만 기존 작업 재검증과 일정 부담 큼 | 이번 마감에는 채택 제안 안 함 |

## 4. 데이터 설계

기존 DB는 data/data_points/conversations 모두 0건으로 확인했다. 데이터 선택을 따로 하지 않은 상황이므로 **서울 일별 평균기온, 2026-06-01~2026-09-30, 122일, ℃**를 기본 제안한다. [Open-Meteo Historical Weather](https://open-meteo.com/en/docs/historical-weather-api)의 재분석 데이터임을 명시하고 실제 관측소 측정값이라고 표현하지 않는다. 출처·좌표·timezone·수집일·이용조건/표기를 데이터 설명서에 적는다. 승인 후 출처 이용조건과 응답 건수/결측을 검증한다. 100건 미만이면 기간을 확장하고 날짜 범위를 문서와 화면에 맞춘다.

- `data/{id}`: date(YYYY-MM-DD), value(유한수), memo(최대 500자), created_at, updated_at.
- `conversations/{id}`: title, created_at, updated_at, messages[{role,content,timestamp,tools_used}].
- 기존 Firebase 프로젝트 m1-2-cody의 (default), asia-northeast3 DB를 재사용한다. Admin SDK/IAM 경로를 유지하고 만료된 테스트 규칙은 클라이언트 직접 접근 거절을 명시하는 규칙으로 정리한다.
- 데이터셋 원본/정제본을 저장하고 결정적 ID로 적재해 재실행해도 중복이 생기지 않게 한다. 운영 데이터 삭제를 적재 전제로 삼지 않는다.
- 기온에서 증가는 개선/악화를 뜻하지 않는다. 추세를 최근 7개 측정값의 방향으로 설명하고 합계는 계산 지표임을 구분한다.
- 현재 메시지 배열 구조를 유지해 마감을 지킨다. 최대 200개/직렬화 900,000바이트를 상한으로 하며, 초과 시 기존 메시지를 자르지 않고 새 대화 안내를 반환한다. 서비스 호출 전 여유 검사, 생성 후 실제 바이트 재검사. 동시 갱신은 트랜잭션으로 보존한다.

## 5. 구성과 인터페이스

브라우저(바닐라) → FastAPI 라우터 → 공용 서비스 → Firestore/OpenAI.
MCP 클라이언트 → 별도 Python stdio 어댑터 → 동일 FastAPI 읽기 API.

- data_summary 서비스: 정렬·통계·추세·프롬프트용 요약을 한 구현으로 공유.
- conversations 서비스: 수동 저장과 chat 자동 저장이 동일 검증/저장 규칙 사용.
- ai_chat 서비스: 요약 주입, 최근 20개 문맥, 도구 루프, 시간/토큰 상한.
- POST conversations 제안 계약: `{title?: string, messages: [{role: 'user'|'assistant', content: string}]}` → 201 ConversationDetail. 서버가 ID·타임스탬프 생성. 비어 있는 messages 및 system/tool 역할은 422. 사용자가 전달한 tools_used는 신뢰하지 않는다.
- 기존 chat 응답 `{conversation_id, reply, tool_calls_used}`와 목록/상세 형식을 유지한다.
- MCP는 query_data_points/get_data_summary 읽기 도구만 노출한다. Firestore 키/GPT 키 없이 API_BASE_URL로 기존 API를 조회한다. 도구 호출 근거를 문서화하며 모델의 비공개 사고 과정은 수집하지 않는다.
- MCP는 [공식 Python SDK](https://github.com/modelcontextprotocol/python-sdk)의 검증된 안정 버전을 고정한다. 별도 optional requirements로 본체 의존성과 분리한다. 로컬 stdio와 독립 SDK 클라이언트로 프로토콜 연결을 증명한다.

## 6. 환경변수와 운영 제안

| 위치 | 변수/설정 |
|---|---|
| backend/.env, Render 비밀 설정 | OPENAI_API_KEY, FIREBASE_SERVICE_ACCOUNT_JSON |
| 백엔드 일반 설정 | OPENAI_MODEL(기존 gpt-4o-mini 유지, 사용 가능 여부 확인), ALLOWED_ORIGINS, LOG_LEVEL |
| 호환 | CORS_ORIGINS를 이전 이름으로 지원. 두 이름이 서로 다르면 설정 오류로 알림 |
| 프론트 빌드/Vercel | API_BASE_URL. 브라우저에 공개되는 URL이며 비밀 키를 함께 넣지 않음 |
| MCP 로컬 실행 | API_BASE_URL. URL/timeout만 필요, 서버 비밀 키 불필요 |

비용/시간 기본 제안: 생성 1회당 최대 출력 600토큰, 도구 라운드 최대 3회, 라운드당 도구 최대 3개, 전체 chat 90초, 개별 SDK 호출 최대 20초, SDK 자동 재시도 0. 전체 시간의 남은 양에 맞춰 개별 timeout을 줄인다. 프론트 chat timeout은 120초를 유지한다. IP별 chat 분당 6회 제한을 단일 Render 프로세스에 적용하고 제한은 429로 안내한다. 분산 운영까지 확장하지 않는다. 실키 검증은 기본 최대 사용자 질문 5회(각 질문의 도구 루프는 위 제한 이내)이며 추가 호출이 필요하면 사유를 기록한다. 서버 상한만으로 계정 전체 과금을 보장하지 않으므로 실제 단가/잔액을 확인하되 계정 과금 설정을 임의 변경하지 않는다.

기존 예외 상세를 화면에 그대로 노출하지 않고 서버 로그에는 키를 남기지 않는다. 공개 데모에는 공개 데이터와 시연 대화만 사용한다. 로그인·멀티사용자·외부 쓰기 도구는 이번 범위에 추가하지 않는다.

## 7. GitHub·VS Code 작업 방식

승인 후 채팅 작업공간의 `app/`을 별도 clone으로 만들고 원본 커밋과 원격을 확인한다. 원본 폴더와 그 .env/venv는 보존한다. 자격증명이 필요한 경우 원본 .env를 화면 출력 없이 새 작업공간의 gitignored .env로 복사하되 추적/아티팩트에 포함하지 않는다. 새 가상환경은 다시 만든다.

`codex/ai-assistant-completion` 브랜치에서 작업하고 VS Code에 app 폴더와 Python 인터프리터를 연결한다. .vscode의 launch/tasks로 로컬 API·프론트 실행과 테스트를 재현한다. 기능별 검증 뒤 커밋하고 GitHub 초안 PR로 변경을 검토 가능하게 만든다. 공개 저장소 푸시 전 비밀정보/개인 파일을 확인한다. Git push가 연결된 자동 배포를 일으킬 수 있으므로 기존 Render/Vercel 연동부터 확인한다.
